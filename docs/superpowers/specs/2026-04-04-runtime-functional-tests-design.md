# Runtime Functional Tests Design

## Goal

补强 `utl_socket`、`utl_tpool`、`utl_timer` 的运行期功能测试，让当前测试集不只覆盖参数校验和最小 happy path，还能覆盖更接近真实运行中的异常和关闭场景。

## Scope

本次只增加测试，不修改对应模块的公开 API，也不主动改变生产逻辑。

本次新增的测试目标限定为 5 个：

- `test_utl_socket.c`
  - 对端关闭后的收发行为
  - 大包和分段收发行为
- `test_utl_tpool.c`
  - 真实任务执行和 `taskEndCb` 回调
  - 慢任务执行中关闭线程池
- `test_utl_timer.c`
  - 回调慢于周期时的稳定性

不在本次范围内的内容：

- 新增 benchmark、吞吐统计或延迟报表
- 改造 `utl_socket`、`utl_tpool`、`utl_timer` 的实现
- 引入新的测试框架
- 扩展到 `ent_db`、`ent_log`、`ent_thread` 等其他模块

## Current Gaps

### 1. `utl_socket`

当前测试只有 localhost 的最小回环，能说明基本可用，但不能说明连接建立后的异常行为是否正确。

已知缺口：

- 对端主动关闭后，本端 `UTL_Recv` 和 `UTL_Send` 的结果不明确
- 大数据量、多次发送、多次接收没有覆盖
- 不能确认“部分发送/部分接收”的调用方式是否被当前 API 正确暴露

### 2. `utl_tpool`

当前测试主要通过 stub 验证线程池初始化、失败清理和默认线程数，没有验证“任务是否真的被 worker 执行完”。

已知缺口：

- `taskCb` 是否真实执行
- `taskEndCb` 是否按预期执行
- 慢任务运行期间 `UTL_TPoolClose` 是否能稳定退出

### 3. `utl_timer`

当前测试验证了 one-shot 和 periodic 的基本行为，但没有覆盖回调执行慢于周期的情况。

已知缺口：

- 是否发生重入
- 是否出现异常高频补触发
- `UTL_TimerClose` 在慢回调存在时是否仍然稳定

## Approaches Considered

### A. 先补功能与异常测试

做法：

- 只写针对现有 API 的功能测试
- 先验证行为边界，再决定是否需要改实现

优点：

- 风险最小
- 最贴合当前仓库已有测试风格
- 能直接回答“功能是否正确”

缺点：

- 本轮不给出性能数据

### B. 功能测试和性能测试一起补

做法：

- 在功能测试之外加入 timer 精度和 tpool 吞吐测试

优点：

- 一轮得到更多结论

缺点：

- 结果容易受机器环境波动影响
- 当前测试框架不适合把性能阈值直接进 `ctest`

## Chosen Approach

采用方案 A：本轮只补功能与异常测试，不做性能基准。

## Detailed Design

### `test_utl_socket.c`

新增两个测试。

#### 对端关闭测试

场景：

1. 建立 localhost TCP 连接
2. 服务端 accept 成功
3. 服务端关闭已 accept 的连接
4. 客户端执行一次 `UTL_Recv`
5. 客户端再执行一次 `UTL_Send`

验证目标：

- 不崩溃
- `UTL_Recv` 能返回“连接已关闭”的可观察结果
- `UTL_Send` 在对端已关闭后返回失败或 0 字节，具体断言依据当前 API 实际行为确定

说明：

由于现有 API 没有统一 errno 包装，这个测试以“返回码和字节数是否稳定可观察”为主，不强行引入新契约。

#### 大包分段收发测试

场景：

1. 建立 localhost TCP 连接
2. 客户端发送显著大于当前最小样例的数据量
3. 服务端循环接收直到拿满预期字节数

验证目标：

- 总字节数正确
- 数据内容一致
- 多次 `recv` 拼接后的内容与原始 buffer 一致

### `test_utl_tpool.c`

现有文件使用大量 stub。本次保留这种风格，但为“真实任务执行”改为尽可能接近真实 worker 行为。

新增两个测试。

#### 任务执行和结束回调测试

场景：

1. 初始化线程池
2. 投递 1 个简单任务
3. 任务修改共享计数并返回固定值
4. `taskEndCb` 记录结束回调是否被触发
5. 关闭线程池

验证目标：

- `taskCb` 被执行
- `taskEndCb` 被执行
- 返回值被写入调用方提供的 `MSG_ID_T`

实现约束：

- 如果现有 stub 阻止真实 worker 运行，则优先把测试改为使用真实 `ENT_Thread*` / `UTL_*` 依赖，而不是继续只靠创建次数断言

#### 慢任务关闭测试

场景：

1. 初始化线程池
2. 投递至少 1 个会 sleep 的慢任务
3. 任务开始执行后调用 `UTL_TPoolClose`

验证目标：

- `UTL_TPoolClose` 返回
- 不死锁
- 任务线程和线程池资源被回收

说明：

这个测试以“关闭路径不挂死”为主，不把任务一定执行完作为强约束，避免和现有实现语义冲突。

### `test_utl_timer.c`

新增一个慢回调周期测试。

#### 慢回调周期稳定性测试

场景：

1. 初始化 timer 子系统
2. 创建 periodic timer
3. timer 回调内部主动 sleep，持续时间大于 timer 周期
4. 运行一段有限时间后删除 timer 并关闭子系统

验证目标：

- 没有明显重入迹象
- 命中次数处于合理区间，而不是异常飙升
- `UTL_TimerDelete` 和 `UTL_TimerClose` 能正常返回

说明：

这个测试不要求严格测量 jitter 或精度，只验证“不会失控”和“关闭可完成”。

## Error Handling

- 新增测试沿用当前测试风格：返回非 0 代表失败，并打印原因
- 对于系统调用差异较大的行为，测试优先断言“稳定可观察的行为”，不强行定义新错误码
- 如果发现现有实现行为不稳定，先保留失败测试，再单独进入修复流程

## Testing Strategy

严格按 TDD 执行：

1. 先在对应测试文件中加入新的失败用例
2. 单独运行对应测试目标，确认红灯是预期失败
3. 只补最小测试支撑代码
4. 单目标绿灯后，再补下一个测试
5. 最后运行全量 `ctest --output-on-failure`

建议执行顺序：

1. `socket` 对端关闭
2. `tpool` 真实任务执行
3. `tpool` 慢任务关闭
4. `timer` 慢回调周期
5. `socket` 大包分段收发

## Risks

- `tpool` 当前测试是 stub 驱动，切到真实 worker 行为时可能暴露已有线程同步问题
- `socket` 与 `timer` 的时间相关测试在慢机器上可能需要放宽阈值
- 某些平台对“对端关闭后再次 send”的返回表现不同，断言需要基于当前支持平台收敛

## Success Criteria

- 5 个新增测试场景全部纳入现有测试集
- 单测能够稳定复现对应功能行为
- 全量 `ctest --output-on-failure` 通过
- 测试结论能明确回答：
  - `socket` 对端关闭和大包收发是否正常
  - `tpool` 任务执行和关闭路径是否正常
  - `timer` 慢回调场景是否基本稳定
